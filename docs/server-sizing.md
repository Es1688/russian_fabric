# Минимальные характеристики сервера (VPS)

Дата расчёта: 2026-10-18. Основание — анализ кода и конфигураций репозитория
(профиль нагрузки снят с актуального состояния `main`).

## Итог

| Ресурс | Минимум (впритык) | Рекомендуется |
|---|---|---|
| CPU | 1 vCPU (допустим shared/burstable) | 1 vCPU |
| RAM | 512 МиБ + swap 512 МиБ | **1 ГиБ** |
| Диск | 5 ГиБ SSD (при регулярной очистке старых образов) | **10 ГиБ SSD** |
| Сеть | любой тариф (< 1 ГБ/мес) | любой |

Достаточно самого дешёвого тарифа любого хостера (1 vCPU / 1 ГиБ / 10 ГиБ) —
он покрывает нагрузку с многократным запасом. Конфигурация 512 МиБ / 5 ГиБ
работоспособна только при включённом swap и после закрытия рисков из раздела
«Риски минимальной конфигурации».

## Профиль нагрузки (факты из кода)

На сервере постоянно работают Docker daemon и ровно один контейнер с одним
asyncio-процессом Python 3.12 (`python -m max_news_bot.main`), внутри которого
живут все циклы приложения:

- **Long polling MAX** — одно висящее соединение по 30 с
  (`max_news_bot/bot/polling.py`, `max_news_bot/max_api/client.py`), ~120
  HTTP-запросов/час, загрузка CPU ≈ 0.
- **Слот-шедулер** — тик 45 с, несколько мелких SQLite-запросов
  (`max_news_bot/bot/slot_scheduler.py`, `TICK_SECONDS = 45`).
- **Daily summary и бэкап** — тик 60 с, срабатывают раз в сутки (22:40 и
  23:10 МСК соответственно: `max_news_bot/bot/daily_summary.py`,
  `max_news_bot/bot/db_backup.py`).
- **Healthcheck** — короткоживущий Python-процесс каждые 30 с, читает SQLite
  (`infra/compose.prod.vps.yml`, `max_news_bot/scripts/healthcheck.py`).
- **Публикация** — 4–6 постов/день (6 активных рубрик, `daily_cap: 6` в
  `max_news_bot/config/rubrics.yaml`).

Пиковые окна (внешние API — процесс в основном ждёт сеть, а не считает):

- **19:00 МСК** — дайджест: 7 RSS-фидов последовательно + до 25 LLM-вызовов за
  попытку (OpenRouter → Yandex AI Studio по fallback, ≤ 800 токенов на ответ) —
  `max_news_bot/rubrics/digest.py`, `max_news_bot/writers/fallback.py`.
- **07:05 МСК** — погода: 1 батч-запрос Open-Meteo (или до 7 параллельных на
  fallback met.no) — `max_news_bot/weather/`.
- **23:10 МСК** — `VACUUM INTO` бэкап SQLite (`max_news_bot/bot/db_backup.py`).

Что сервер **не** нагружает:

- LLM-писательство и генерация картинок — полностью внешние API (OpenRouter,
  Yandex AI Studio, fal.ai); локального инференса нет.
- Зависимости — ~15 лёгких пакетов (aiohttp, feedparser, pyyaml,
  python-dotenv); pillow/numpy/lxml отсутствуют.
- Сгенерированные картинки — ≤ 10 МиБ транзитно в RAM
  (`MAX_IMAGE_BYTES`, `max_news_bot/images/base.py`), на диск пишутся в
  `data/generated/` и удаляются после публикации (TTL 7 дней). В текущем
  `config/rubrics.yaml` генерация картинок не включена (только локальные
  открытки из `data/postcards/`).

## Расчёт по компонентам

### CPU

Средняя загрузка < 5 % одного ядра: все «тяжёлые» операции — ожидание ответов
внешних API. Единственные всплески CPU — разбор RSS-фидов feedparser в потоках
(7 фидов × ≤ 20 записей, доли секунды) и ежедневный `VACUUM INTO` для БД
размером < 1 МиБ. Хватает 1 vCPU любого типа, включая shared.

### RAM

| Потребитель | RSS |
|---|---|
| dockerd + containerd + containerd-shim | 120–180 МиБ |
| Контейнер бота (Python 3.12 + aiohttp + feedparser + SQLite) | 60–120 МиБ |
| Healthcheck-субпроцесс (транзитно, раз в 30 с) | +15–25 МиБ |
| ОС (systemd, sshd, journald) | 100–150 МиБ |
| **Итого фактическое потребление** | **~350–450 МиБ** |

Отсюда: 1 ГиБ — комфортно; 512 МиБ — впритык, обязателен swap (например,
`fallocate -l 512M /swapfile`) и явный `mem_limit` на контейнер.

### Диск

| Статья | Размер |
|---|---|
| ОС (Ubuntu/Debian minimal) + Docker engine | ~2.5–3 ГиБ |
| Образ приложения (python:3.12-slim + uv + зависимости) | ~250 МиБ распакованный (~90 МиБ при pull) |
| Накопление старых образов при деплоях | ~90 МиБ сжатых на релиз (см. риск № 2) |
| SQLite (сейчас 72 КиБ, рост ~0.1–0.3 МиБ/мес) + 7 ежедневных бэкапов | < 10 МиБ |
| Логи контейнера | до правки — неограниченно; после — ≤ 40 МиБ (3 × 10 МиБ) |

Диск решает Docker, а не данные бота: 10 ГиБ — без забот; 5 ГиБ — только при
регулярной очистке старых образов.

### Сеть

Long polling (~120 запросов/час, тела малы) + RSS-тела (7–9 фидов, сотни КиБ на
фид) + LLM JSON (~1–3 МиБ/мес) ≈ десятки–сотни МБ/мес. Любой трафик.

## Риски минимальной конфигурации

1. **Ротация логов.** Без `logging.max-size` драйвер json-file растёт
   неограниченно и однажды занимает весь диск.
   *Закрыто:* `logging: json-file [max-size 10m, max-file 3]` во всех
   compose-файлах (`infra/compose.prod.vps.yml`, `infra/compose.prod.yml`,
   `max_news_bot/docker-compose.yml`).
2. **Накопление старых образов.** Каждый деплой тянет новый sha-тег (~90 МиБ),
   старые не удалялись.
   *Закрыто:* `docker image prune -a -f` в `.github/workflows/docker.yml` после
   успешного подъёма контейнера. VPS выделен под бота; `prune -a` удаляет
   только образы, не используемые запущенными контейнерами.
3. **Отсутствие лимита памяти.** На 512 МиБ аномалия процесса приводит к
   OOM-kill; `restart: unless-stopped` маскирует проблему.
   *Закрыто:* `mem_limit: 256m` в compose (steady-state контейнера 60–120 МиБ,
   лимит с двукратным запасом).

## Проверка на сервере после деплоя

```bash
docker stats --no-stream maxnewsbot        # RSS контейнера (ожидание 60–120 МиБ)
free -m                                    # итог по RAM
df -h /var/lib/docker                      # итог по диску
docker system df                           # образы/логи/тома
du -sh /opt/maxnewsbot/data/backups        # бэкапы (7 × размер БД)
```
