# Workflow субагентов для реализации автономного канала

Дата: 2026-10-09. Статус: черновик на согласование.

Реализует план `docs/plans/2026-10-09-autonomous-channel.md` (Этапы 0–5 + интеграция).
Механизм: dynamic workflow (CreateWorkflow), субагенты работают по кодовой базе репозитория,
детерминированные гейты — командами. Тестовая неделя (Этап 6), сбор банка контента, деплой —
вне workflow.

## 1. Разделение ответственности

| Кто | Что |
|---|---|
| workflow | исследование (Этап 0), код и тесты Этапов 1–5, интеграция, независимая проверка, отчёт |
| оператор | решения по итогам исследования (RSS-лист, картинки), сбор/проверка банка контента, коммит и деплой (с подтверждения), тестовая неделя |
| ведущий агент (лид) | запуск workflow, разбор эскалаций, финальный прогон pytest, коммит через git-finish-task |

Правила безопасности внутри workflow:

- субагенты не выполняют git-коммитов и пушей (фиксируется в промптах); изменения
  остаются в рабочей копии до ревью лидом;
- `world.run` ограничен командой `uv` (только pytest) — сетевых установок и Docker нет;
- секреты из `.env` субагенты не читают и не выводят; тесты пишутся без реальных API-ключей;
- `RUBRICS_ENABLED` в тестах и дефолтах — всегда false; боевая БД `max_news_bot/data/`
  не трогается (тесты используют tmp-пути/фикстуры).

## 2. Структура: один скрипт, два запуска

Один параметризованный workflow-скрипт, две фазы запуска:

1. **Запуск A «Исследование»** (`mode=research`) — Этап 0 плана: три параллельных
   исследователя, итог — отчёт с вариантами решений. Останавливается; оператор
   подтверждает RSS-лист и режим картинок.
2. **Запуск B «Реализация»** (`mode=build`) — Этапы 1–5: DAG фаз «реализатор(ы) → гейт →
   ремонт-цикл», в конце независимая проверка и отчёт. Решения оператора входят
   аргументами (`rss_sources`, `images_mode`).

Разделение нужно потому, что Этапы 3–4 зависят от решений, которые нельзя принимать
за оператора. Оба запуска идут одним скриптом — имена субагентов стабильны, повторный
запуск/правка (AmendWorkflow) переиспользует кэш.

## 3. Запуск A: исследование (Этап 0)

| Фаза (как видит оператор) | Субагент | Задача | Результат |
|---|---|---|---|
| Исследование API и источников | research-max-uploads | MAX Bot API `POST /uploads`: формат, токен, лимиты, как расширить `max_api/client.py` | `ResearchNote` |
| | research-yandexart | YandexART: доступность, endpoint (синхр./асинхр.), стоимость, ограничения | `ResearchNote` |
| | research-rss | кандидаты федеральных «мягких» RSS (культура, наука, природа, спорт-победы, добрые истории): доступность, формат, условия ссылок | `RssShortlist` |
| Сводка решений для оператора | — (скрипт) | сборка markdown-отчёта с рекомендациями | артефакт, `return WorkflowReport` |

Тип `ResearchNote`: `topic`, `findings[]` (факт + ссылка-источник), `recommendation`,
`risks[]`. Каждый клейм-исследователь обязан прикладывать URL источника; неподтверждённые
заявления помечаются `unconfirmed`.

## 4. Запуск B: реализация (Этапы 1–5)

Общий паттерн фазы: параллельные реализаторы (fresh subagent на модуль) → быстрый гейт
(targeted pytest) на каждого → сильный гейт фазы (полный pytest) → ремонт-цикл.

| Фаза | Субагенты (параллельность) | Содержание | Зависимости |
|---|---|---|---|
| Каркас: миграция и конфиг рубрик | impl-migration ∥ impl-rubric-config | миграция v4 (`slot_runs`, `digest_items`, `rubric_state`, `content_bank`, лог фильтров) + репозитории; схема конфига рубрик, загрузчик, startup-валидация вкл. взаимоисключаемость `RUBRICS_ENABLED`/legacy (§8 плана) | — |
| Каркас: слотовый планировщик | impl-scheduler | тик 30–60 с, grace, порядок слотов в тике, UNIQUE-захват, статусы вкл. `publishing`/`unknown_delivery`, recovery без повторной отправки вслепую, перенос breaker/автопаузы из `core/factory.py` | миграция + конфиг |
| Каркас: команды и наблюдаемость | impl-admin | расширение `/factory` (pause/resume/run/status/retract + аргумент рубрики, обратная совместимость), сводка 22:40, heartbeat (`scripts/healthcheck.py`) | планировщик |
| Погода | impl-weather-ometeo → impl-weather-metno; impl-weather-template ∥ | провайдер Open-Meteo batch на 7 точек + интерфейс провайдера; резерв met.no (7 запросов); таблица правил, шаблон, восход/закат формулой, валидатор (§4 плана) | конфиг рубрик |
| Утро и ночь | impl-bank-pipeline ∥ impl-generative; impl-images после решений | пайплайн банка + сезонность + антиповтор (Jaccard ≥ 0.7 из кода); генеративный пайплайн (persona, prompt_overlay, до 2 перегенераций, резервный пост); картинки: метод загрузки в `max_api`, publisher с image_ref (режим из `images_mode`) | планировщик |
| Хорошие новости | impl-news-fetch → impl-news-filters → impl-digest | RSS + дедуп с shadow-изоляцией (отдельная БД/таблицы, §14 Этап 0 плана); цепочка фильтров (стоп-лист, тематические исключения, LLM-классификатор ×2, свежесть, повторы) + лог фильтров; выпуск 3–4 пунктов, валидатор ссылок и чисел, деградация | планировщик, `rss_sources` |
| Дневные рубрики | impl-topic-day ∥ impl-second-post | тема дня (topics_by_weekday, календарь, «в этот день» по `event_date`); второй пост (ротация рецепт/совет/вопрос/факт) | утро/ночь + новости |
| Интеграция и переключатель режимов | impl-cutover | `main.py`: запуск рубрикового контура за `RUBRICS_ENABLED`, legacy-циклы под флагом, fail-fast при конфликте; обкатка на рубрике-заглушке через dry-run/тестовый target | все фазы выше |
| Независимая проверка реализации | reviewer → confirmer ∥ fixer | свежий ревьюер сверяет полный diff с планом (полнота §14, отклонения, новые баги); каждое high-находку подтверждает независимый confirmer по коду; подтверждённые — на fixer | интеграция |
| Итоговый отчёт | — (скрипт) | markdown-отчёт: что сделано по фазам, coverage плана, verified/notCovered | все |

Ремонт-цикл (на каждую фазу, лимит 2 итерации): сильный гейт упал → фикс-агент фазы
(персистентный, `fixer-<фаза>`) получает stderr целиком → повторный гейт. Не ушло за
две итерации — эскалация лиду, фаза помечается красной, следующие зависимые фазы
не стартуют.

## 5. Гейты (world.run)

| Уровень | Команда | Когда |
|---|---|---|
| быстрый | `uv run pytest max_news_bot/tests/<тестируемый модуль>` | после каждого реализатора |
| сильный | `uv run pytest` (полный suite) | конец каждой фазы |
| финальный | `uv run pytest` + тесты startup-валидации конфига (валидный конфиг рубрик грузится; конфликт `RUBRICS_ENABLED`+legacy роняет запуск) | после интеграции, до независимой проверки |

В репозитории нет линтера и CI тестов не гоняет — полный pytest и есть сильнейшая
проверка. Сборку Docker-образа лид при желании прогоняет после workflow отдельно.

## 6. Типизированные результаты

- `StageResult`: `files_changed[]`, `tests_added[]`, `plan_items_covered[]` (ссылки на
  пункты плана), `notes` — у каждого реализатора;
- `ReviewFinding`: `where`, `what`, `evidence`, `severity` (low/medium/high),
  `status` (verified/unconfirmed) — у ревьюера/confirmer'а;
- финальный `return` — `WorkflowReport { conclusion, findings[], verified[], notCovered[] }`.

`plan_items_covered` нужен независимому ревьюеру: он сверяет эти ссылки с §14 плана и
ловит пропущенное.

## 7. Артефакты

- board «Прогресс реализации»: карточка на фазу, статусы (делается/готово/ремонт/блок);
- markdown-отчёт (primary) — итоговый, длинная форма того, что в `return`;
- в запуске A — markdown-отчёт с решениями (primary).

## 8. Аргументы workflow

| Аргумент | Тип | Default | Смысл |
|---|---|---|---|
| `mode` | string | `research` | `research` \| `build` |
| `rss_sources` | string | — | путь к подтверждённому оператором yaml источников (для build, фаза новостей) |
| `images_mode` | string | `bank` | `bank` \| `yandexart` — режим картинок (для build) |

## 9. Эскалации и отказы

- невозможный гейт / противоречивые инструкции → субагент эскалирует лиду (не «прёт»
  до лимита и не имитирует успех — фиксируется в persona);
- падение провайдера ретраится рантаймом само; эскалации это не дублируют;
- упавший запуск чинится правкой скрипта + AmendWorkflow (кэш по именам агентов),
  не перезапуском с нуля.

## 10. Критерии готовности запуска B

- все фазы зелёные, полный `uv run pytest` проходит;
- независимый ревьюер подтвердил покрытие всех пунктов §14 Этапов 1–5 (или отклонения
  перечислены и объяснены);
- ни одной незакрытой high-находки; unconfirmed-находки перечислены в отчёте;
- dry-run рубрики-загушки не публикует в боевой канал (проверяется тестом target).

После этого: лид прогоняет полный pytest ещё раз, ревьюит diff, коммит по git-finish-task
с подтверждения оператора. Тестовая неделя — вручную по §13 плана.
